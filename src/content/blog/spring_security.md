`Spring Security`와 JWT를 제대로 이해하려면 단순히 로그인 API를 만들거나

`SecurityFilterChain`을 설정하는 수준에서 벗어나야 한다.

예를 들어, 아래와 같은 질문에 스스로 답할 수 있어야 한다.

- `Spring Security`는 어떻게 `Controller`에 도달하기 전에 요청을 가로채는가 ?
- `AuthenticationManager`, `AuthenticationProvider`, `SecurityContextHolder`는 각각 어떤 역할을 하는가 ?
- JWT는 서버에 저장하지 않는데, 어떻게 사용자를 인증하는가 ?
- JWT 서명이 올바르더라도 거부해야 하는 경우는 무엇인가 ?
- `STATELESS`로 설정했는데, 왜 쿠키와 CSRF 문제가 여전히 발생할 수 있는가 ?
- Access Token을 탈취당했을 때 서버는 어떻게 대응해야 하는가 ?
- 여러 서버가 동시에 Refresh Token을 갱신하면 어떤 문제가 생기는가 ?
- JWT 방식은 정말 세션 방식보다 뛰어난가 ?

이번 글은 위 질문들을 이해하고, 스스로 답할 수 있도록 하는 것을 목표로 하겠다.

# 1. Spring Security를 이해하기 위한 기초

## 1. Spring Security란 무엇인가 ?

Spring Security는 Spring 기반 애플리케이션에서 인증(Authentication), 인가(Authorization), 일반적인 보안 위협에 대한 방어를 지원하는 보안 프레임워크이다.

일반적으로 다음과 같은 기능을 제공한다.

- 사용자 인증 및 인증 상태 관리
- URL과 HTTP 메서드에 따른 접근 제한
- 메서드 단위 권한 검사
- 비밀번호 해싱 및 검증
- 세션 관련 보안 기능
- CSRF 공격 방어
- 보안 HTTP 응답 헤더 설정
- OAuth2 및 OpenID Connect 연동
- JWT와 Opaque Token을 이용한 API 보호

여기서 중요한 사실이 하나 있는데, 바로 **Spring Security는 JWT 전용 프레임워크가 아니라는 것**이다.

JWT 없이도 세션 기반 로그인을 구현할 수 있고, JWT가 아닌 다른 인증 수단을 사용할 수 있다.

반대로, JWT를 사용한다고 해서 반드시 Spring Security를 사용해야 하는 것도 아니다.

다만 Spring 애플리케이션에서 인증/인가를 구현한다면, 검증된 Spring Security의 기능을 활용하는 편이 일반적으로 안전하고 유지보수에도 용이하다.

## 2. 인증(Authentication)과 인가(Authorization)

보안에서 가장 먼저 구분해야 할 개념이다,

### 2.1 인증(Authentication)

인증은 사용자가 주장하는 신원을 확인하는 과정이다.

예를 들어, 사용자가 아래와 같은 정보를 서버에 전달했다고 가정해보자.

```json
{
    "email": "example@example.com",
    "password": "password123@"
}
```

서버는 입력받은 이메일에 해당하는 사용자를 조회하고, 제출된 비밀번호와 저장된 비밀번호 해시를 비교한다.

일치하면 인증에 성공한다.

이 외에도 다른 인증 방법도 존재한다.

- 아이디와 패스워드
- 생체 인증과 패스키
- OAuth2 로그인을 통한 외부 인증
- 세션 쿠기를 이용한 기존 로그인 상태 확인
- Bearer Token을 이용한 요청 인증

즉, 인증은 반드시 아이디와 패스워드를 입력하는 과정만을 의미하는 게 아니다.

사용자가 최초 로그인한 이후에 JWT를 전송하는 것도 요청에 대한 인증 과정이다.

### 2.2 인가

인가는 인증된 주체에게 특정 행동을 수행할 권한이 있는지 확인하는 과정이다.

게시글 서비스를 예로 들어보겠다.

| 요청 | 인증 | 인가 |
| --- | --- | --- |
| 공개 게시글 조회 | 불필요할 수 있음 | 누구나 허용 |
| 게시글 작성 | 로그인 필요 | 작성 권한 확인 |
| 자신의 게시글 수정 | 로그인 필요 | 본인 소유인지 확인 |
| 타인의 게시글 삭제 | 로그인 필요 | 관리자 또는 정책상 허용된 사용자만 가능 |
| 관리자 페이지 접근 | 로그인 필요 | 관리자 권한 필요 |

여기서 중요한 차이가 있다.

인증에 성공했다고 해서 모든 작업을 수행할 수 있는 건 아니다.

로그인한 일반 사용자가 관리자 API에 접근하려고 하면, 인증에는 성공했더라도 인가에는 실패해야 한다.

### HTTP 401과 401

| 상태 코드 | 의미 | 예시 |
| --- | --- | --- |
| `401 Unauthorized` | 유효한 인증 정보가 없음 | 토큰 없음, 만료, 서명 검증 실패 |
| `403 Forbidden` | 요청이 거부됨 | 일반 사용자가 관리자 API 접근 |

여기서 주의해야 할 점은 `403 Forbidden` 이 항상 인증 성공을 의미하는 것은 아니다.

CSRF 검증 실패 등 다른 이유로도 403이 발생할 수 있다.

Spring Security에서는 다음 컴포넌트가 관련되어 있다.

- `AuthenticationEntryPoint` : 인증이 필요한 상황을 처리
- `AccessDeniedHandler`: 접근 거부 상황을 처리

이 둘의 차이는 뒤에서 내부 흐름과 함께 살펴보겠다.

## 3. HTTP는 Stateless인데 로그인 상태를 어떻게 유지할까 ?

이 질문을 이해해야 세션과 JWT가 필요한 이유를 알 수 있다.

### 3.1 HTTP와 Stateless의 특성

HTTP는 기본적으로 각각의 요청을 독립적으로 처리하도록 설계된 프로토콜이다.

예를 들어 아래와 같은 요청이 발생했다고 가정해보자.

```json
POST /login
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "mypassword"
}
```

이후 서버가 로그인 성공 응답을 반환했다.

그다음, 사용자가 요청한다.

```json
GET /mypage
```

HTTP 프로토콜 자체만으로는 두 번째 요청이 첫 번째 요청을 보낸 사용자와 동일한 사람인지 알 수 없다.

따라서 사용자 신원을 요청 사이에서 연결하는 수단이 필요하다.

대표적인 방식은 다음과 같습니다.

1. 세션 ID를 이용하는 방식
2. 서명된 토큰을 이용하는 방식

두 방식 모두 HTTP 자체의 Stateless 특성을 없애는 것이 아니라, 애플리케이션 계층에서 인증 상태를 처리하는 방식이다.

---

## 4. 세션 기반 인증

세션은 서버가 사용자 인증 상태를 관리하는 대표적인 방법이다.

!image.png

### 4.1 로그인 과정

1. 사용자가 ID와 패스워드를 전송한다.
2. 서버가 사용자 정보를 확인한다.
3. 인증에 성공하면 세션을 생성한다.
4. 서버가 세션 저장소에 인증 정보를 보관한다.
5. 클라이언트에는 세션 ID가 담긴 쿠키를 전달한다.

클라이언트는 세션의 모든 정보를 저장하지 않고, 다음과 같은 쿠키를 보유한다.

```
Set-Cookie: JSESSIONID=abc123; HttpOnly; Secure; SameSite=Lax
```

이후, 브라우저는 쿠기 전송 조건이 충족되면 자동으로 세션 ID를 서버에 전달한다.

그리고 서버는 세션 ID를 통해 사용자 정보를 찾는다.

따라서 매번 아이디와 패스워드를 입력하지 않아도 인증 상태를 유지할 수 있다.

### 4.2 세션 방식의 장점

가장 큰 장점은 서버가 로그인 상태를 직접 통제할 수 있다는 것이다.

예를 들어 사용자가 로그아웃하면 서버에서 세션을 무효화할 수 있다.

또한 사용자가 탈퇴하거나 관리자에 의해 계정이 정지된 경우에도 기존 세션을 무효화하는 등의 처리가 가능하다.

### 4.3 세션 방식의 단점

서버 측에서 인증 상태를 관리할 저장소가 필요하다.

서버가 하나라면 메모리에 저장할 수도 있겠지만, 서버가 여러 대라면 각 서버가 같은 세션 정보를 확인할 수 있어야 한다.

다만 이 단점이 세션 방식의 본질적인 결함이라는 뜻은 아니다.

Spring Session과 Redis 등을 활용하면 여러 서버에서 세션을 공유할 수 있고,

대규모 서비스에서도 충분히 활용할 수 있다.

세션 기반 인증은 오래된 방식이기 때문에 JWT로 교체해야 하는 기술이 아니다.

요구사항에 따라서는 세션 방식이 JWT보다 더 적합할 수도 있다.

## 5. JWT 기반 인증

JWT는 JSON Web Token의 약자로, JSON 기반의 정보를 당사자 사이에서 전달할 수 있도록 설계되었다.

서명된 JWT를 사용하면 서버는 토큰에 포함된 정보가 신뢰하는 발급자에 의해 서명되었고, 그 이후 변조되지 않았는지를 확인할 수 있다.

대표적으로 아래와 같은 흐름을 가진다.

```
[최초 로그인]

Client
  |
  | ID / PW
  v
Server
  |
  | 사용자 인증 성공
  | JWT 발급
  v
Client

[이후 API 요청]

Client
  |
  | Authorization: Bearer <JWT>
  v
Server
  |
  | 서명 및 Claim 검증
  | 인가 검사
  v
Controller
```

### 5.1 JWT는 서버에 저장하지 않아도 되는가

JWT의 서명 검증 자체에는 서버 측의 토큰 저장소가 필요하지 않다.

예를 들어 JWT에 아래와 같은 정보가 들어 있다고 가정해보자.

```json
{
  "sub": "100",
  "role": "USER",
  "iat": 1791763200,
  "exp": 1791764100
}
```

서버는 토큰의 서명을 검증한 후, 신뢰할 수 있는 사용자 식별자와 권한 정보를 확인할 수 있다.

하지만 여기에는 주의할 점이 있는데

서명을 검증했다고 해서 해당 계정이 지금도 활성 상태인지, 권한 변경이 있었는지, 토큰이 폐기되었는지까지 자동으로 알 수 있는 건 아니다.

이러한 요구사항이 있다면 DB 또는 Redis를 조회하는 추가 로직이 필요하다.

따라서 “JWT를 사용하면 데이터베이스에 접근할 필요가 없다.” 는 문장은 틀렸다고 볼 수 있다.

차라리

> JWT를 사용하면 매 요청마다 서버 저장소를 조회하지 않고도 토큰 자체의 유효성을 검증할 수 있다. 다만, 보안 정책에 따라 추가적인 서버 상태 조회가 필요할 수도 있다.
> 

정도로 정리할 수 있겠다.

### 5.2 세션과 JWT 비교

| 항목 | 세션 기반 인증 | 서명된 JWT 인증 |
| --- | --- | --- |
| 인증 상태의 근거 | 서버 측 세션 | 검증된 토큰과 필요 시 서버 상태 |
| 요청에 전달하는 값 | 세션 ID | JWT |
| 서버 저장소 | 일반적으로 필요 | 단순 토큰 검증에는 불필요 |
| 즉시 로그아웃 | 세션 무효화 가능 | 추가 설계 필요 |
| 권한 변경 반영 | 세션 갱신·무효화 정책에 따름 | 토큰 갱신 또는 추가 조회 필요 |
| 여러 서버 확장 | 공유 세션 저장소 등 활용 | 각 서버가 서명 검증 가능 |
| 토큰 크기 | 세션 ID는 보통 작음 | Claim에 따라 커짐 |
| 탈취 위험 | 세션 ID 탈취 위험 | Bearer Token 탈취 위험 |

JWT가 서버를 무조건 더 빠르게 만들어주는 건 아니다.

서명 검증에도 계산 비용이 발생하고, JWT의 크기가 커지면 네트워크 비용도 증가한다.

여기에 토큰 블랙리스트 조회가 계정 상태 조회까지 추가한다면 Stateless 인증의 장점이 줄어들 수 있다.

### 5.3 가장 중요한 구분

지금까지의 내용을 다음과 같이 정리할 수 있다.

- Spring Security: 인증/인가와 보안 기능을 제공하는 프레임워크
- 세션: 서버에서 상태를 관리하는 인증 유지 방식
- JWT: 정보를 전달하는 표준 토큰 방식
- Bearer Token: 토큰을 가진 사람이 사용할 수 있는 자격 증명 방식

참고로 Bearer Token은 반드시 JWT일 필요는 없다.

또한 JWT라는 형식 자체가 로그인을 수정해주는 것은 아니다.

인증이 성공한 뒤에 토큰을 발급하거나, 이미 발급된 토큰을 검증하는 로직은 별도로 필요하다.
